# 面试流程看板

一个可运行的最小版本，跑通完整业务流程：**查看看板 → 新建投递 → 指定跟进人 → 推进面试阶段 → 安排面试时间与会议 → 查看最新进度**。

看板的列就是面试阶段——`HR screen / 在线测评 / 一面 / 二面 / 三面 / 四面 / HRBP 面 / Offer 审批中`，终点是 `已发 Offer` 或 `已结束`。**这些阶段全部可以在页面上自由增删、改名、调序**，不是写死的枚举。每张卡片是一次投递（公司 + 岗位），卡片下挂着每一轮面试的独立记录：面试时间、时长、线上会议链接或线下地点、面试官、结果与评价。

单一 Go 服务，前后端不分离：同一个进程既渲染看板页面（SSR 首屏），也提供 JSON 接口供页面交互使用。数据落在 SQLite 文件里，刷新页面和重启服务后都还在。

## 快速开始

```bash
go run ./cmd/server            # 默认 :8080，数据文件 data/app.db
open http://localhost:8080     # 自动跳转到 /boards/JOBHUNT
```

可选参数：`-addr :8080`、`-db data/app.db`、`-mode debug|release`。

想用「AI 录入」（把 HR 邮件整段粘进来自动建卡）再多配一个环境变量：

```bash
OPENAI_API_KEY=sk-... go run ./cmd/server
```

`OPENAI_BASE_URL`（默认 `https://api.openai.com/v1`）和 `OPENAI_MODEL`（默认 `gpt-4o-mini`）可选，
指向任何 OpenAI 兼容网关都行。**不配 key 也能跑**，只是页面上不显示「✨ AI 录入」入口，其余功能不受影响。

想把面试同步到 Google 日历，再配一组 OAuth 客户端：

```bash
GOOGLE_CLIENT_ID=xxx.apps.googleusercontent.com \
GOOGLE_CLIENT_SECRET=xxx \
GOOGLE_REDIRECT_URL=http://localhost:8080/oauth/google/callback \
go run ./cmd/server
```

在 [Google Cloud Console](https://console.cloud.google.com/apis/credentials) 建一个
**OAuth client ID（Web application）**，启用 Google Calendar API，把上面那个
`GOOGLE_REDIRECT_URL` 原样填进「Authorized redirect URIs」——两边必须一字不差。
**同样是不配也能跑**：日程页照常打开，只显示看板这一半。

首次启动会自动建表并写入种子数据：一个看板 `JOBHUNT`、十个默认阶段、一名成员 `我`、四条示例流程，以及三条面试记录（分别覆盖「已排期」「已过期待回填」「已通过」三种形态）。

> 如果本地还留着旧版任务看板的 `data/app.db`，删掉它再启动，才能拿到这套面试流程的种子数据。

跑测试：

```bash
go vet ./... && go test ./...
```

## 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| HTTP 框架 | `github.com/gin-gonic/gin` | 路由分组、参数绑定、中间件齐全 |
| 数据库 | SQLite（`modernc.org/sqlite`，纯 Go 驱动） | 单文件持久化，无需 cgo，无需外部服务 |
| 模板 / 静态资源 | `html/template` + `go:embed` | 编译成单个二进制，模板自带 XSS 转义 |
| 前端 | 原生 JS + CSS，无框架无打包 | 前后端不分离，不引入 Node 构建链 |
| 测试 | 标准库 `testing` + `httptest` | 无第三方断言库 |

## 模块划分

模块用 Go package 隔离，依赖方向单向：`server → api/web → board/stage/application/member → workflow/platform`，无循环依赖。

```
cmd/server/                 启动入口：flag、日志、优雅关闭
internal/server/            路由装配：中间件 → 页面路由 → /api 分组 → 静态资源
internal/web/               页面模块：board.html + CSS/JS（go:embed），SSR 首屏
internal/api/               接口模块：入参绑定、调用 service、组织响应
internal/ingest/            AI 录入模块：把粘贴的文本解析成草稿，确认后再落库
internal/ai/                OpenAI Chat Completions 客户端（标准库 net/http，无 SDK）
internal/calendar/          日程模块：Google 授权保管、面试推成日程、两边拼成时间线
internal/gcal/              Google OAuth2 + Calendar v3 客户端（同样是标准库直发）
internal/board/             看板模块：看板信息 + 进展摘要统计
internal/stage/             阶段模块：面试阶段的增删改序，workflow 的数据来源
internal/member/            成员模块：成员列表、新增成员、解析「当前用户」
internal/application/       面试流程模块：投递创建/维护、跟进人、阶段流转、面试轮次、操作日志
internal/workflow/          流程模块：阶段类型 + 流转规则校验（纯函数，不碰数据库）
internal/platform/sqlitedb/ 连接、PRAGMA、建表迁移、一次性数据修补、种子数据
internal/platform/apperr/   领域错误类型（错误码 / HTTP 状态 / 中文提示 / 字段）
internal/platform/ginx/     统一错误处理中间件、响应封装、当前用户中间件
internal/platform/ordering/ 列内浮点位置计算，卡片与阶段列共用
```

**gin 只出现在 `server` / `api` / `web` / `ginx` 四个包**，service 与数据访问层不 import gin，因此业务逻辑可以脱离 HTTP 单测，将来换框架的成本也可控。

`application` 包不直接依赖其他业务包的实现，只声明它需要的最小接口（`MemberChecker` / `BoardChecker` / `StageProvider`），由 `server` 注入。

## 数据模型

```
boards              一个看板 = 一套阶段配置 + 它下面的全部流程
stages              可配置的面试阶段：key（稳定标识）、label（可改名）、kind、color、
                    requires_owner、skippable、position。按 board_id 隔离
applications        一次投递：公司、岗位、渠道、备注、当前 stage_key、意向度、跟进人
google_accounts     Google 日历的授权凭证，单用户只有一行（CHECK id = 1）
interview_rounds    每一轮面试：stage_key + stage_label 快照、面试时间、时长、
                    方式（线上/现场/电话）、会议链接、地点、面试官、结果、评价、
                    google_event_id（在 Google 日历上对应的事件）
application_events  操作日志
members             可被指定为跟进人的成员
```

两个刻意的设计：

- **阶段改名不动 `key`**。`applications.stage_key` 通过复合外键 `(board_id, stage_key)` 指向 `stages(board_id, key)`，改 label 不影响任何卡片。
- **面试记录存 `stage_label` 快照**。阶段以后改名或被删掉，历史记录里仍然写着当时那一轮叫什么。

## 数据流

以「把卡片从二面拖到三面」为例：

```
浏览器拖拽 → 乐观更新 DOM → PATCH /api/applications/{id}/stage {to, index}
  → gin 绑定入参 → api.MoveApplication → application.Service.Move
  → stage.Service.FlowOf(boardID) 读取当前阶段配置        ← 配置改完立刻生效
  → workflow.Flow.Validate(from, to, hasOwner)            ← 规则在这里，唯一事实来源
  → 事务：更新 applications.stage_key/position
         + 目标是面试阶段则自动建一条「待安排」的 interview_rounds
         + 写入 application_events（操作日志）
  → 重新查询该看板的全部列与进展摘要，随响应一并返回
  → 前端用返回的看板整体重绘（列本身可能被增删，只填卡片不够）
失败时：ginx.ErrorHandler 输出 {"error":{code,message,field}}
  → 前端弹出红色 toast 显示后端提示，并拉取服务端数据回滚卡片位置
```

任何一次变更（新建 / 编辑 / 流转 / 排期 / 改阶段配置）的响应里都直接带上最新看板，前端一次请求即可让「结果真实可见」，也避免了本地状态和数据库不一致。

## 阶段配置与流转规则

阶段存在 `stages` 表里，页面顶部「⚙ 配置阶段」可以改名、换色、调序、切换类型、增删阶段，以及逐列开关「需跟进人」与「可跳过」。每个阶段有一个 `kind`：

| kind | 含义 | 特殊待遇 |
|---|---|---|
| `normal` | 普通阶段 | 无 |
| `interview` | 面试阶段 | 卡片移入时自动建一条「待安排」的面试记录 |
| `terminal_success` | 终态 · Offer | 任何阶段可直达 |
| `terminal_fail` | 终态 · 结束 | 任何阶段可直达 |

规则集中在 `internal/workflow/workflow.go`（纯函数，接收阶段快照构造 `Flow`），服务端强制校验，前端只用来把非法选项置灰：

1. **默认只允许相邻流转**：按列顺序进/退一格。跨阶段跳跃返回 `409 INVALID_TRANSITION`。
2. **`skippable` 的列可以被跨过去**：中间隔着的列**全部**标了「可跳过」时才放行，进退两个方向一视同仁。默认配置里「在线测评」「四面」「HRBP 面」是可跳过的——所以 `HR screen → 一面` 直接成立，而 `HR screen → 二面` 仍然被拒（中间的「一面」不可跳过）。
3. **终态可以直达**：任何阶段都可能突然拿到 Offer 或被挂，所以 `已发 Offer` / `已结束` 不受相邻限制。
4. **终态可以退回**：误标之后能拉回任意非终态阶段。
5. **`requires_owner` 的阶段必须先有跟进人**，否则返回 `409 OWNER_REQUIRED`。默认配置里「一面」开着这条，可以在阶段配置里逐列开关——原来写死的「进入进行中必须先有负责人」现在是一条可配置规则。
6. 同列内拖动视为纯排序调整，不写流转日志，也不重复建面试记录。
7. **新建流程可以指定起始阶段**（`stage_key`，缺省第一列）。新卡片没有历史，「从一面开始」是个起点而不是流转，所以不受相邻性约束——猎头直接约一面、内推跳过初筛都很常见。`requires_owner` 照样要守。

删除阶段有两条护栏：阶段下还有卡片时返回 `409 CONFLICT`；看板至少要留一个非终态阶段，否则新投递没有落脚点。

## AI 录入

顶部「✨ AI 录入」把一段自由文本（HR 邮件、面试邀约、测评通知）变成一张卡片。分两步：

1. `POST /api/boards/:key/ingest/parse` — 只调模型，返回一份**草稿**，不写任何数据。
2. `POST /api/boards/:key/ingest/confirm` — 用户在界面上改完草稿后提交，走建卡 / 流转 / 排期。

拆成两步是刻意的：模型会抠错公司名、认错阶段，草稿阶段出错只是界面上改一改，落库之后出错就得手动回滚。确认这一步模型已经不参与，落库调的都是 `application` 的既有方法，重复公司名、`requires_owner`、非法流转照样会被拦下来，操作日志也和手工操作一模一样。

几处收敛模型输出的地方：

- **阶段清单随提示词一起下发**，返回的 `stage_key` 不在本看板里就直接丢掉——模型编不出这个看板没有的列。
- **截止日期和面试时间分开**。测评邮件常写「链接 8 月 28 日过期」，那不是面试时刻；`deadline` 单独一个字段，折进这一轮的备注，`scheduled_at` 保持为空（卡片显示「待安排」）。
- **公司名做模糊匹配，但不做部分词匹配**：规整（转小写、去标点、抹掉「有限公司」之类后缀）后先精确匹配，再退到一次宽松匹配。宽松匹配要求**首词对上**——公司名不管中英文都是「字号 + 业务描述」，字号在最前面，它才是身份，所以 `Anker` 命中 `Anker Innovations`，而 `Innovations` 不命中。「对上」的标准按语种分开：拉丁词必须**整词相等**，中文词允许**前缀**（至少两个字）。这条区分是必要的——英文靠空格分词，`BIT` 恰好是 `Bitdeer` 的前缀纯属巧合，按前缀匹配会把两家毫不相干的公司凑成一对；而中文公司名不加空格，`易点天下` 和 `易点天下网络科技` 说的就是同一家。命中就复用那张卡，**只补空字段，不覆盖已填的内容**。匹配不了译名（`小米` 对不上 `Xiaomi`），那要靠词典，不在本轮范围。
- **建议的流转不合法时不硬来**：给出提示，阶段留空，用户可以先把这一轮录进去再手动处理。
- **流转进面试阶段时系统会自动挂一条「待安排」**，录入会把信息补到那一条上，不在同一列里建两条。
- **跟进人默认是「我」**：AI 录入是本人在录自己的面试，不传 `owner_id` 就兜底成当前用户，`requires_owner` 的阶段也就自然满足了。显式传 `0` 表示「就是不要跟进人」，不会被兜底盖掉。

用 structured outputs（`response_format: json_schema`, `strict: true`）约束输出，省掉「模型偶尔多包一层 markdown」这类补丁逻辑。测试注入假模型，不打真网络。

## 日程页与 Google 日历

`/boards/:key/calendar`（看板顶部「📅 日程」进）。**默认一周一屏**，七列固定——
空的那天也占一格，否则「这周哪天是空的」反而看不出来。上面铺两种东西：

- **看板的面试**：按阶段配色，带流程编号、方式、结果；没同步的给一个「同步到日历」按钮
- **Google 日历上已有的会议**：统一灰调，点标题跳去 Google

**时间重叠的条目会被标上「撞期」**——这正是把两边放一起的意义。
还没定时间的面试不在时间线上，单独列在底部提醒；**卡片已经走到终态
（拿到 Offer 或已结束）的不算**——那是流程中断留下的残影，不会再发生，
继续催人去约只会把真正要处理的几条淹掉。

### 同步方向：只推出去

看板是事实源。排期 / 改期 / 把结果标成「已取消」/ 删除轮次，都会自动写回日历：

| 看板上的动作 | 日历上发生什么 |
|---|---|
| 新排一场面试 | 建一条日程，event id 记在 `interview_rounds.google_event_id` |
| 改时间 / 改会议信息 | 用记下的 event id 去 update |
| 时间清空、标成已取消 | 把日程撤掉 |
| 删除这一轮 | 删库之前先撤日程——删完就查不到 event id 了 |
| 在 Google 那边手动删了日程 | update 撞 404，退回去重建一条 |

**同步失败不让看板操作失败**：日历是外部系统，它挂了不该导致排期存不下来。
出错只把原因挂在响应的 `calendar_warning` 里，前端弹一句提示，可以到日程页手动重试。
同理，日历拉不回来时日程页只挂个 warning，看板的面试照常显示。

### 凭证

`google_accounts` 表只有一行（`CHECK (id = 1)`），存 refresh token。
access token 过期时自动用 refresh token 换新的并落库。授权时带
`access_type=offline&prompt=consent`——少了它 Google 只给一小时有效的 access token，
重启就断；所以拿不到 refresh token 时当场报错，而不是先让人用上再突然失效。
断开连接会一并清掉所有 `google_event_id`：换个账号再连，旧 id 指向的事件已经够不着了。

## 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/boards/:key` | 看板页面（SSR，支持 `?stage=&owner=&upcoming=1` 筛选） |
| GET | `/api/boards/:key` | 看板信息 + 进展摘要 |
| GET | `/api/boards/:key/board` | 全部阶段列 + 卡片 + 摘要，支持筛选 |
| POST | `/api/boards/:key/applications` | 新建投递（可同时指定跟进人、意向度、起始阶段） |
| POST | `/api/boards/:key/ingest/parse` | AI 解析粘贴的文本，只返回草稿，不写库 |
| POST | `/api/boards/:key/ingest/confirm` | 把确认后的草稿落库：建卡 / 复用已有卡 → 流转 → 录入这一轮 |
| GET | `/api/boards/:key/stages` | 阶段配置 + 可选的阶段类型 |
| POST | `/api/boards/:key/stages` | 新增阶段（缺省插在终态之前） |
| PATCH | `/api/stages/:id` | 改名 / 换色 / 改类型 / 改跟进人要求 / 改是否可跳过 |
| PATCH | `/api/stages/:id/position` | 调整列顺序 |
| DELETE | `/api/stages/:id` | 删除阶段（非空返回 409） |
| GET | `/api/applications/:id` | 流程详情 + 面试轮次 + 操作日志 |
| PATCH | `/api/applications/:id` | 维护公司 / 岗位 / 渠道 / 备注 / 跟进人 / 意向度 |
| PATCH | `/api/applications/:id/stage` | 阶段流转（拖拽与下拉共用） |
| POST | `/api/applications/:id/rounds` | 安排一场面试 |
| DELETE | `/api/applications/:id` | 删除流程（面试记录与操作日志一并清除）|
| PATCH | `/api/rounds/:id` | 改期 / 补会议信息 / 回填结果与评价 |
| DELETE | `/api/rounds/:id` | 删除一条面试记录 |
| GET | `/api/agenda` | 日程数据：面试 + Google 日历，`?from=2026-08-24&days=7` |
| GET | `/api/google/status` | Google 日历连接状态 |
| POST | `/api/google/disconnect` | 断开 Google 日历 |
| POST | `/api/rounds/:id/sync` | 手动把这一轮推到 Google 日历 |
| GET | `/oauth/google/connect` | 302 到 Google 授权页（不在 `/api` 下，是浏览器跳转） |
| GET | `/oauth/google/callback` | OAuth 回调，换 token 后跳回日程页 |
| GET / POST | `/api/members` | 成员列表 / 新增成员 |
| POST | `/api/session/member` | 切换「我是谁」，写 cookie |

面试时间用 RFC3339（`2026-08-25T14:00:00+08:00`）；`scheduled_at` 传空字符串表示退回「待安排」。

错误统一信封：

```json
{"error": {"code": "INVALID_TRANSITION", "message": "不允许从「在线测评」直接流转到「三面」", "field": ""}}
```

- `400 VALIDATION_ERROR`：公司名为空 / 超长、意向度或面试方式取值非法、时间格式不合法、筛选参数不合法
- `404 NOT_FOUND`：看板、流程、面试记录、阶段、跟进人不存在
- `409 INVALID_TRANSITION` / `OWNER_REQUIRED` / `CONFLICT`（删非空阶段、删光非终态阶段、成员重名、同公司同岗位重复投递）
- `500 INTERNAL`：真实原因只写服务端日志，响应里不泄漏内部细节

## 用户角色

本轮不实现注册登录。顶部下拉「我是」切换当前成员，选择写入 cookie，后续所有操作日志都记在该成员名下。成员既是「操作者」，也是卡片上的「跟进人」。成员分 `团队成员` 与 `负责人（lead）` 两种角色——目前两者能力一致，角色主要用于展示与后续扩展权限。

**默认只有一个成员「我」**：这是一个人自己用的求职看板，跟进人默认就是本人。成员这套字段完整保留着，顶部「+ 成员」随时能加人，将来想拉人一起跟进不用改数据模型。旧库里的演示成员 `A / B / C` 由迁移收成一条——`A` 改名为「我」并保留它名下的全部流程与日志，`B / C` 没被引用才删掉。

## 已实现的可选扩展

- **日程页 + Google 日历双向可见**：`/boards/:key/calendar` 一周一屏，看板的面试和 Google 日历上已有的会议铺在同一条时间线上，时间重叠自动标「撞期」
- **排期自动同步**：排期 / 改期 / 删除面试会自动写回 Google 日历，日历那边挂了也不影响看板保存
- **AI 录入**：把 HR 邮件整段粘进来，自动抽出公司、岗位、阶段、时间与截止日期，生成草稿供确认
- **阶段自由配置**：增删改序、改名换色、切换阶段类型、逐列开关「需跟进人」与「可跳过」，改完立刻生效
- **每一轮面试独立记录**：时间、时长、线上会议链接 / 线下地点、面试官、结果、评价，详情抽屉里可查完整历史
- **流程删除**：详情抽屉底部可删掉整条投递，面试记录与操作日志靠外键级联清除
- **一个公司一张卡片**：同一看板内「公司 + 岗位」唯一，重复新建或改名撞车返回 409 并提示已有卡片编号
- 卡片直接展示「下一场面试」：时间 + 会议方式；逾期未回填结果标红；停在面试阶段却没排时间的卡片高亮提醒
- 按跟进人 / 阶段筛选，以及「只看已排期」
- 顶部进展摘要：推进中 / Offer / 已结束 / 近 7 天面试场次 + 已出结果占比进度条
- 流转规则限制（见上）
- 操作日志：创建、指定跟进人、信息修改、阶段流转、排期变更，倒序展示
- 自动化测试：日程页脚本用最小 DOM 桩实跑一遍（页面脚本抛运行时错误会让整页空白，而接口测试照样全绿）、`ingest` 的匹配与时间解析单测（注入假模型，不打真网络）、`workflow` 规则表驱动测试、`stage` 与 `application` 基于真实 SQLite 的集成测试、`api` 层用 httptest 跑完整业务流程与各类错误分支

## 关键取舍

- **阶段 key 自动从标签生成**：中文标签取不出 ASCII slug，会回退成 `stage`、`stage_2`……key 只是内部标识，界面上始终显示 label，够用；要可读的 key 可以后续开放手工填写。
- **流转规则的骨架（相邻 + 可跳过 + 终态直达）是硬编码的**，可配置的只有阶段列表和每列的两个开关。做成「每个阶段自定义允许的下一步」会让配置界面复杂得多，而面试流程本身就是线性的，「可跳过」已经覆盖了「这家公司没有在线测评」这类主要诉求。
- **AI 录入不自动落库**：解析和确认拆成两个接口，多一次点击，换来「模型出错不会污染看板」。也没做「自动定时扫邮箱」——那要接 IMAP / OAuth，超出本轮范围，粘贴已经覆盖主要场景。
- **AI 只做抽取，不做决策**：阶段是它从给定列表里选的，选错了界面上改一下就行；流转合不合法仍由 `workflow` 判定，模型说了不算。
- **日历只推不拉**：Google 那边改了时间不会回流到看板。双向同步要存 etag、处理冲突、加轮询或 webhook，复杂度翻倍，而看板本来就是事实源。日程页把两边并排显示，已经能看出「日历上被人改了」。
- **日程同步是尽力而为，不进事务**：SQLite 事务包不住外部 HTTP 调用。宁可出现「看板存了、日历没同步」并把原因显式告诉用户，也不要为了原子性把排期回滚掉。
- **不做登录鉴权**：用 cookie 表达「当前是谁」。
- **单看板为主**：数据模型和路由都按多看板设计（`/boards/:key`），但没做看板管理页面，首页直接跳转到默认看板。
- **无并发冲突处理**：两人同时编辑同一条流程是后写覆盖先写。后续可用 `updated_at` 做乐观锁。
- **公司 + 岗位唯一只做在 service 层**，没有加数据库唯一索引：加索引会让已经存在重复行的旧库启动即失败。代价是极端并发下两个请求可能同时通过校验。
- **迁移只做加列 + 一次性数据修补**，没有引入迁移框架：`migrations` 表记一行 id，就够保证回填只跑一次、不会覆盖用户后来的选择。表结构本身仍靠 `CREATE TABLE IF NOT EXISTS` 幂等建出来。
- **列内排序用浮点 `position` 取中点**：实现简单，长期频繁插入可能精度耗尽，需要定期重排；本轮数据量下不是问题。
- **看板不分页**：流程量大时一次全量返回，后续需要分页或懒加载。
- **无 CSRF token**：同源演示环境；生产环境需要补。
- **前端有一份卡片渲染逻辑与模板重复**（SSR 首屏 + JS 重绘）：换来了「不带 JS 也能看」和「变更后即时更新」两个好处，代价是两处结构要同步维护。流转下拉已经统一由 JS 填充，规则不再写两遍。

## AI 工具使用方式

本项目使用 Claude Code 辅助完成：

- 需求拆解与方案设计：先把题目里的模块职责、必做项、可选项整理成实现计划（技术选型、目录结构、数据模型、状态机、接口清单、取舍），确认后再动手。改造成面试流程看板时同样先出方案，把「阶段可配置」「每轮独立记录」这两个关键决策确认下来再改代码。
- 代码生成：按「数据层 → 公共能力 → 流程模块 → 业务模块 → 接口层 → 页面层 → 测试」的顺序分步生成，每步都编译验证。
- 验证：AI 生成代码后，通过实际启动服务 + curl 走完整流程（含各类错误分支）核对行为，再补自动化测试固化。

判断与决策由人来做：技术栈（gin + SQLite、前后端不分离）、阶段配置的粒度、流转规则、模块边界、哪些扩展要做，都是先定方向再让 AI 落地，生成结果逐段检查而不是照单全收。
